1. Проверяем сетевые интерфейсы командой: ip -br addr, где опция -br brief (краткий вывод). Получили два сетевых интерфейса: lo и eth0. lo 
(loopback) это виртуальный сетевой интерфейс обратной петли, предназначенный для сетевого взаимодействия внутри самой операционной системы, а eth0 
это виртуальный сетевой интерфейс Ethernet, через который Ubuntu в WSL2 взаимодействует с внешней сетью.

Из интерфейса eth0 видим ip адрес своей Ubuntu 172.21.122.223/20. Где префикс подсети /20 говорит о том, что первые 20 бит IPv4-адреса относятся к 
сети, оставшиеся 12 — к адресам узлов. Маска — 255.255.240.0, адрес сети — 172.21.112.0/20.

Проверяем адрес шлюза по умолчанию командой: ip route.

Ответ команды:

default via 172.21.112.1 dev eth0 proto kernel
172.21.112.0/20 dev eth0 proto kernel scope link src 172.21.122.223

То есть, в данном случае ip адрес шлюза 172.21.112.1 и пакет данных пойдет через интерфейс eth0, который имеет адрес 172.21.122.223.

2. Проверяем доступность шлюза и внешнего адреса 1.1.1.1 по ICMP командой ping. Проверим доступность шлюза: ping -c 4 172.21.112.1

Ответ команды:

PING 172.21.112.1 (172.21.112.1) 56(84) bytes of data.

--- 172.21.112.1 ping statistics ---
4 packets transmitted, 0 received, 100% packet loss, time 3261ms

Вывод: мы не смогли получить ICMP ответ от шлюза. Данный ответ еще не говорит об неисправности шлюза, возможно он блокируется настройками сетевого 
экрана или правилами wsl2.

Проверим ICMP ответ от внешнего ip адреса командой: ping -c 4 1.1.1.1

Ответ команды:

PING 1.1.1.1 (1.1.1.1) 56(84) bytes of data.
64 bytes from 1.1.1.1: icmp_seq=1 ttl=254 time=136 ms
64 bytes from 1.1.1.1: icmp_seq=2 ttl=254 time=158 ms
64 bytes from 1.1.1.1: icmp_seq=3 ttl=254 time=58.1 ms
64 bytes from 1.1.1.1: icmp_seq=4 ttl=254 time=58.1 ms

--- 1.1.1.1 ping statistics ---
4 packets transmitted, 4 received, 0% packet loss, time 3006ms
rtt min/avg/max/mdev = 58.074/102.592/158.170/45.176 ms

Вывод: шлюз не ответил на четыре ICMP Echo-запроса, однако проверка внешнего адреса 1.1.1.1 завершилась успешно. Вместе с выбранным маршрутом через 
172.21.112.1 это подтверждает работоспособность выхода к проверенному адресу. Причина отсутствия ответов от самого шлюза не установлена, а 
фильтрация остаётся предположением.

3. Проверяем разрешение имени через команду getent ahostsv4 example.com и получаем такой ответ:

172.66.147.243  STREAM example.com
172.66.147.243  DGRAM
172.66.147.243  RAW
104.20.23.154   STREAM
104.20.23.154   DGRAM
104.20.23.154   RAW

Вывод: мы видим, что разрешение имен работает.

Проверим файл с инструкцией для разрешения имен командой: cat /etc/nsswitch.conf

Видим, что в файле прописаны строки hosts: files dns. Это значит, что первым делом будет проверен файл hosts. Мы можем посмотреть его по пути 
/etc/hosts. В данном файле мы не обнаружили записи для домена example.com. Это значит, что разрешение имен будет происходить через DNS резловер. Об 
этом говорит вторая запись в строке dns. Проверим, какой адрес у DNS резолвера по пути /etc/resolv.conf. В файле видим строку: nameserver 
10.255.255.254. Получается, что linux идет в файл hosts, видит, что записи о домене example.com отстутствуют и идет получать нужный адрес через DNS 
резловер по адресу 10.255.255.254.

Проверяем получения адреса через DNS сервер командой: dig example.com A +time=3 +tries=1

Получаем ответ:

;; ANSWER SECTION:
example.com.            168     IN      A       172.66.147.243
example.com.            168     IN      A       104.20.23.154

Вывод: получение адреса домена через DNS сервер работает. При том, мы видим, что разрешение имен через getent и команда dig получают одни и теже 
адреса.

4. Теперь проверим TCP работу командой nc -vz -w 3 example.com 443. Тут у нас опция -v показывает подробный вывод от слова verbose, опция -z 
проверяет подключение без передачи данных приложения, а -w задает время ожидания в 3 секунды, от слова wait.

Получили ответ: Connection to example.com (172.66.147.243) 443 port [tcp/https] succeeded!

Успешное соединение подтверждает доступность конкретного адреса 172.66.147.243 на TCP-порту 443 на момент проверки. Транспортный уровень L4 
работает. Разрешение имени домена так же прошло успешно, мы видим это по строке (172.66.147.243). Подпись [tcp/https] обозначает название сервиса 
для порта 443, но не подтверждает работу HTTPS.

Проверяем работу через curl, вводим команду: curl -I -v --connect-timeout 5 --max-time 15 https://example.com

Вывод: мы успешно получили ответ от сервера. Подробный ответ лежит в файле по пути reports/https-check.txt, подтверждающий TLS, проверку сертификата 
и HTTP-ответ.

Из ответа отдельно выделю, что было получено:

DNS работает, имя example.com успешно разрешено в IPv4 адрес.

* Host example.com:443 was resolved.
* IPv4: 172.66.147.243, 104.20.23.154

Было установлено TCP соединение на порт 443.

*   Trying 172.66.147.243:443...
* Connected to example.com (172.66.147.243) port 443

Было установлено защищённое соединение с использованием TLS 1.3. Через ALPN согласовано использование HTTP/2.

* SSL connection using TLSv1.3 / TLS_AES_256_GCM_SHA384 / X25519 / id-ecPublicKey
* ALPN: server accepted h2

Сертификат соответствует домену example.com, проверка сертификата прошла успешно.

*  subject: CN=example.com
*  subjectAltName: host "example.com" matched cert's "example.com"
*  SSL certificate verify ok.

Отправлен HTTP запрос методом HEAD, сервер вернул статус 200.

* using HTTP/2
> HEAD / HTTP/2
> Host: example.com
< HTTP/2 200

5. Общий вывод.

Мы подтвердили ICMP ответ от адреса 1.1.1.1, разрешение имени example.com, получение DNS ответа и TCP подключение к 172.66.147.243:443. Отдельная 
HTTPS проверка подтвердила установление TLS соединения, успешную проверку сертификата и получение ответа на HEAD запрос. ICMP ответы от шлюза не 
получены, причина не установлена. Данные результаты подтверждают работоспособность проверенных направлений и протоколов на момент проверки. 
Доступность остальных ресурсов сети не проверялась.
